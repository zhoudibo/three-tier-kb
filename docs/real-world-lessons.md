## 一、那些让人抓狂的坑

### 坑 1 · 正则批量改 Markdown，损坏 28 篇文章

**现象**：一次批量给文章补 `<figure>` 标签的脚本，用正则扫描全文替换。
结果 28 篇文章的 HTML 结构被打乱，图文错位。

**根因**：Markdown 里嵌 HTML 时，正则无法理解嵌套结构。
`<div>` 里有 `<p>` 里还有 `<img>`，正则一旦贪婪匹配就跨越了边界。

**修复**：

```python
# ❌ 不要这样
content = re.sub(r'<div class="x">.*?</div>', replace, content, flags=re.DOTALL)

# ✅ 用 DOM 解析
from bs4 import BeautifulSoup
soup = BeautifulSoup(content, "html.parser")
for div in soup.find_all("div", class_="x"):
    div.replace_with(BeautifulSoup(replace, "html.parser"))
content = str(soup)
```

**沉淀成规则**：Markdown 内嵌 HTML 时，**禁止用正则扫描改写**，必须用 DOM 解析。

### 坑 2 · 过滤集合漂移，产生数百条幽灵删除

**现象**：某次同步后，vault 里有数百个「应该存在」的文件消失了。

**根因**：实时监听（watchdog）和手动重扫（re-scan）用了**两套不同的目录过滤集合**。
一次 `pip` 重装改变了 `.git` 内部文件的 mtime，监听器把这些当成「workspace 内容变更」，
上报了一大批删除。

**修复**：所有扫描路径**必须走同一个过滤函数**，物理上消除过滤漂移的可能。

```python
def walk_files(root):
    """唯一的文件遍历入口 —— 所有调用方共用"""
    for dirpath, dirnames, filenames in os.walk(root):
        dirnames[:] = [d for d in dirnames if d not in EXCLUDE_DIRS]
        for fn in filenames:
            if Path(fn).suffix.lower() in SYNC_EXTS:
                yield Path(dirpath) / fn
```

**沉淀成规则**：过滤集合必须是**单一真相源**。

### 坑 3 · 带空格的文件名静默丢失

**现象**：同步报告「成功」，但 vault 里少了几个文件，且不报错。

**根因**：

```bash
for f in $(find . -name "*.md"); do   # ← 空格处被拆开
    process "$f"
done
```

文件名 `第 1 批 成果.md` 被拆成三个参数，脚本只处理了 `第`。

**修复**：

```bash
find . -name "*.md" -print0 | while IFS= read -r -d '' f; do
    process "$f"
done
```

Python 侧同理：

```python
# ❌
for f in subprocess.check_output("find . -name '*.md'").split("\n"):
    ...

# ✅
out = subprocess.check_output(["find", ".", "-name", "*.md", "-print0"])
for f in out.decode().split("\0"):
    ...
```

**沉淀成规则**：**任何 shell 遍历都要处理空格**，这是默认动作不是特殊情况。

### 坑 4 · frontmatter 缺失，文件被误判为孤儿

**现象**：图谱修复时扫描出 59 个孤儿文件，但其中大部分看起来「明显该有链接」。

**根因**：这些文件的 frontmatter 不全，扫描器无法识别它们是知识卡片，
于是既不统计入链也不统计出链 → 全部落入孤儿。

**修复顺序**（关键）：

```
先补 frontmatter → 再建 cluster → 孤儿自然归零
```

而不是先急着加链接。

**实测数据**：frontmatter 完整率 `8% → 52% → 100%`，三轮。
孤儿数 `59 → 22 → 5 → 2 → 0`，四轮。**孤儿减少靠的是补字段，不是加链接。**

### 坑 5 · 独立资源索引文件，自己变成孤儿

**现象**：为「图片资源」新建了一个 `图片索引.md`，专门列出所有图片。
结果这个文件自己没人指向，成为图谱上一个新孤儿。

**更糟的是**：每新增一类资源就要改一个文件，N 类资源 N 次维护。

**修复**：撤销该文件，把内容合并回已有的项目索引，用内嵌 wikilink。

**沉淀成规则**：**不要为每类资源单独建索引文件**。
正确做法是在已有项目索引里内嵌 wikilink。新建独立索引文件是反模式。

---

### 坑 6 · 扫描报告「32 个文件」，真实有效的只有 2 个

**现象**：孤儿扫描报告列出 32 个散落文件。

**根因**：扫描时没过滤 `.git/`，`.git/objects/` 里几十个文件被算进来了。

**修复**：统一过滤 + 报告时**必须区分「原始数量」和「有效数量」**。

**沉淀成规则**：报告里同时给两个数，否则会做出错误判断。

---

### 坑 7 · 哈希基线用错了对象

**现象**：脚本日志显示「字节一致」，但实际 workspace 内容变了。

**根因**：拿**日志的 md5** 当基线。日志 md5 衡量的是「脚本输出稳定性」，
不是「文件字节稳定性」。两者只是碰巧相关。

**修复**：基线必须是**文件内容的 hash**。

```python
h = hashlib.md5(content.encode()).hexdigest()
```

**沉淀成规则**：**哈希基线的对象必须是你想守护的数据本身**。
日志不是、文件数不是、mtime 也不是。

---

### 坑 8 · FTS5 中文检索精度崩了

**现象**：在会话库里搜中文关键词，返回的全是无关结果。

**根因**：SQLite FTS5 默认 `unicode61` 分词器把中文切成**单字**，
于是「视频生成」和「视」「频」「生」「成」几乎等价。

**修复**：

```sql
CREATE VIRTUAL TABLE messages_fts USING fts5(
    content, tokenize='trigram'
);
```

**另外三个必做细节**：
1. 必须用 `rowid` JOIN 虚拟表，不能直接查原表
2. 必须 `LIMIT`（10-20）且过滤 `m.role='user'`，否则助手的长回复淹没用户原话
3. `started_at` 是 unix epoch，用 `time.time() - N*86400` 做时间截断

---

### 坑 9 · 所有出链塞进正文，污染内容

**现象**：为了提高图谱密度，把 wikilink 直接插进技术文档正文。

**结果**：文档变得莫名其妙，读起来像索引而不是内容。

**修复**：关联关系**只放在项目索引里**，正文保持干净。
正文里的链接只保留真正有语义关联的。

**沉淀成规则**：**密度靠索引层的 cluster 互链提升，不靠污染正文。**

## 二、那些验证过的结论

### 结论 1 · 每个文件 ≥3 条出链才能在图谱里居中

在 Obsidian 力导向布局下实测：
出链 1-2 条的文件仍在边缘徘徊，**≥3 条**才稳定居中。
密度指标（总出链数 / 文件数）**≥2.0** 是结构健康的保守下限。

### 结论 2 · 同目录互链 > 跨目录互链 > 按类型分 cluster

修复孤儿的三种策略效果对比：

| 策略 | 效果 | 原因 |
|---|---|---|
| 按文件类型分 cluster | 差 | 跨目录不密集 |
| 跨目录挑 5 个文件互链 | 差 | 数量太少，形不成 cluster |
| **同目录全部互链** | **好** | 形成密集网络 |

**先试同目录。** 同物理目录 = 同 cluster 是自然映射。

### 结论 3 · 并行 subagent 处理批量同类任务

用 subagent 并行给每个项目生成索引，相比单 agent 顺序处理：
**快约 8 倍**，且**遗漏率更低**。

### 结论 4 · 从零重建索引永远自愈

增量更新的漂移是**单向棘轮**（漏掉的删除补不回来）。
从零重建每次都产出与磁盘完全一致的结果。
30 秒的重建成本，换来「漂移不可能累积」。

### 结论 5 · 门禁的 WARN 才是主要工作量

真实库第一次体检通常是 `4 PASS / 7 WARN / 1 FAIL`。
**FAIL 通常只有一项（敏感文件），WARN 才是真正的整理工作量**。
迭代 3-6 轮把 FAIL 清零即可放行。

### 结论 6 · 入链救不了出链缺失

一个文件被 10 处引用但自己从不引用任何人 —— 它照样会被力导向布局推到边缘。
**高入链 ≠ 居中。必须自己出链。**

## 三、作业顺序（验证过的最优解）

```
1. 备份 vault
2. 补 frontmatter（9 字段）        ← 先做这个，后面才有效
3. 建项目索引 + cluster 互链
4. 重建 L0 元索引                  ← 一条命令自动修好索引一致性项
5. 跑门禁 → 修 FAIL → 再跑
6. 孤儿归零 → 断链清零 → 密度达标
7. 人工在 Obsidian 里验证图谱
```

**为什么第 4 步放在第 5 步前面**：
索引一致性（第 11 项检查）跑一次 `--build` 就自动 PASS。
先 build 再 gate，能省掉一大半 WARN。

## 四、门禁检查项速查

| # | 检查 | PASS 条件 |
|---|---|---|
| 1 | 库结构与入口 | 有索引或总导航 |
| 2 | 孤儿文件 | 孤儿数 = 0 |
| 3 | 断链 | 断链数 = 0 |
| 4 | frontmatter 9 字段 | ≥90% 齐全 |
| 5 | 出链覆盖 | ≥80% 的卡有出链 |
| 6 | 入链覆盖 | ≥70% 的卡被引用过 |
| 7 | 敏感文件与凭据 | 无（**必须 FAIL**） |
| 8 | 重复标题 | 无重复 |
| 9 | 空文件 / 近空文件 | 无 |
| 10 | 日期有效性 | 无未来日期 |
| 11 | 索引一致性 | 元索引 MD 数 = 实际 MD 数 |
| 12 | 图谱密度 | ≥2.0 出链/节点 |

## 五、给未来的自己

1. **先备份再改**。批量操作前 `cp -R` 一份，回滚成本几乎为零。
2. **不要相信「脚本说没问题」**。去 Obsidian GUI 里看一眼。
3. **frontmatter 是检索的地基**。补它比加链接更有效。
4. **过滤集合要单一真相源**。
5. **删除文件要先授权**。知识库里的东西可能有别人在引用。
