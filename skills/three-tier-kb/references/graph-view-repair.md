# Graph View 孤儿修复

Obsidian 图谱连不上、文件散落外围、节点堆在边上 —— 这份文档讲怎么修，以及**为什么**会这样。

---

## 一、根因不是「组织问题」，是布局算法

Obsidian Graph View 用**力导向布局**（force-directed layout）。节点位置由引入力与斥力共同决定：

| 节点形态 | 布局结果 |
|---|---|
| 高入链 + 高出链 | 居中、稳定 |
| 高入链 + **零出链** | **被推到边缘** ← 这就是问题 |
| 真正孤立（无任何链接） | 孤儿节点 |
| 枢纽（高出链） | 居中，有吸引力 |

**关键认知**：一个文件被 10 个地方引用（高入链），但它自己**不引用任何人**（零出链），
它照样会被推到图谱边缘。**入链救不了出链缺失。**

修复 = 给每个文件**在它的功能组内**补出链。

## 二、四步协议

### Step 1 · 扫描孤儿

```bash
python3 $S/kb_gate.py ~/Documents/my-vault   # 第 2 项 = 孤儿文件
```

或用索引引擎的图谱索引：

```bash
python3 $S/kb_index.py --vault ~/Documents/my-vault --build
# .kb_meta/graph_index.json → nodes.isolated_md_files / isolated_samples
```

**注意**：索引文件（`索引.md` / `index.md` / `AGENTS.md`）本身就是枢纽，
它指向别人、没人指向它是正常的。扫描时要排除它们。

### Step 2 · 按文件类型定策略

| 文件类型 | 策略 |
|---|---|
| 新建的文件 | 在项目索引里加一条出链 |
| 历史文件（不该动内容） | 加进已有项目索引的 cluster 段 |
| 同批次的文件 | 用 cluster 互链（见下） |
| 索引/枢纽文件 | **不动**，它已经是枢纽 |
| 纯二进制（图片等） | 在项目索引里按类型建 cluster 引用 |

### Step 3 · 应用 cluster 互链

**策略 A · 同目录互链（推荐）**

同物理目录的文件天然相关，形成密集网络：

```markdown
### 📂 2026-04_首批文章发布（38 个 Python 脚本）

- 🐍 `[[fix_p463_transitions.py]]`
- 🐍 `[[fix_p118_p313_transition_v2.py]]`
- 🐍 `[[fix_p313_regen.py]]`

**🔗 Cluster 内部关联**：
`[[fix_p463_transitions.py]]` ↔ `[[fix_p118_p313_transition_v2.py]]` ↔ `[[fix_p313_regen.py]]`
```

**策略 B · 功能分组**（文件确实散在多个目录时）

```markdown
### 🔧 修复工具
`[[fix_p463_transitions.py]]` ↔ `[[fix_p118_p313_transition_v2.py]]` ↔ `[[fix_p313_regen.py]]`
```

**决策规则**：先试策略 A。同目录 = 同 cluster 是自然映射。
只有当文件真的散在多个目录时才用策略 B。

> **真实教训**：
> - 第一版按**文件类型**分 cluster → 跨目录不密集，图谱还是散的
> - 第二版**跨目录 5 个文件**互链 → 数量太少，形不成 cluster
> - 第三版**同目录全部互链** → 才真正形成密集网络

### Step 4 · 验证归零

```bash
python3 $S/kb_gate.py ~/Documents/my-vault   # 第 2 项必须 PASS
```

**每修一步就重跑一次扫描。** 不要修完所有再验证 —— 你会不知道是哪一步改坏的。

## 三、三条必须遵守的规矩

### 1. 不要在代码注释里塞 wikilink

```python
# ❌ 污染实际代码
"""# AGENT-LINK: [[项目索引]]"""

# ✅ 关联放在项目索引里
```

如果已经被污染了，清理：

```python
import re
content = re.sub(r'"""# AGENT-LINK:[^"]*?"""', '"""', content, flags=re.DOTALL)
```

### 2. 不要建独立资源索引

```markdown
❌ 成果/文件索引.md
❌ 成果/图片索引.md
❌ 成果/资源清单.md
```

**为什么是反模式**：
1. 独立索引文件自己没人指向 → **它自己变成孤儿节点**
2. 每加一类资源就要新建/改一个文件 → N 类资源 N 次维护
3. 与已有项目索引重复

**正确做法**：在**已有的**项目索引里内嵌 wikilink。

> 真实教训：曾为图片资源建了独立的「图片索引.md」，
> 违反了「不新建独立索引文件」的要求，最后撤销合并回项目索引。

### 3. 每个文件 ≥3 条出链

力导向布局下，**≥3 条出链**才能稳定居于中心。
只有 1-2 条出链的文件仍可能在边缘徘徊。

## 四、非 MD 文件的特殊处理

Obsidian Graph View 对非 MD 文件：

- **有入链** → 被识别为节点
- **无出链** → 被推到边缘

图片、Excel、PDF、脚本文件都无法自己写 wikilink（除非是 MD）。

**解决方案**：在项目索引里**按类型建立 cluster**，把同类文件集中列出：

```markdown
### 🖼️ 图片资源（12 个）
`[[封面图]]` ↔ `[[架构图]]` ↔ `[[流程图]]` ↔ `[[数据截图]]` ↔ ...

### 📊 数据文件（5 个）
`[[运营数据.xlsx]]` ↔ `[[选题库.json]]` ↔ ...
```

这样这些文件就有了入链，出现在图谱里。

## 五、过滤：为什么 32 个文件其实是 2 个

扫描时如果没过滤 `.git/`，会看到 `.git/objects/...` 里几十个文件，
误判成「散落的外围文件」。

> **真实教训**：一次扫描报告「32 个文件」，其中 30 个是 `.git` 内部文件。
> 真实有效文件只有 2 个。**报告时必须区分「原始数量」和「有效数量」。**

统一过滤集合：

```python
EXCLUDE_DIRS = {
    '.git', '.obsidian', '.vscode', '.idea', 'node_modules', '__pycache__',
    '.venv', 'venv', 'site-packages', '.cache', '.pytest_cache', '.Trash',
    'dist', 'build', '.next', 'coverage', '.nyc_output', 'target',
}
```

**所有扫描必须走同一个过滤函数。** 过滤漂移 = 幽灵条目
（实测一次 pip 重装造成 数百条幽灵删除）。

## 六、修复效果参考

一次真实修复（数百文件的库）：

| 轮次 | 操作 | 孤儿数 |
|---|---|---|
| 初始 | — | 59 |
| 第 1 轮 | 补核心文档 frontmatter（覆盖率 8%→52%） | 22 |
| 第 2 轮 | 批量补齐 `type` 字段 | 5 |
| 第 3 轮 | 补齐 `source` 字段 | 2 |
| 第 4 轮 | 重建同目录 cluster 网络 | **0** |

**关键**：孤儿减少靠的不是加链接，而是**先补齐 frontmatter**。
frontmatter 缺失 → 扫描器认不出这些卡片 → 它们是「孤儿」。

所以修复顺序应该是：

```
补 frontmatter → 重建 cluster → 验证归零
```

## 七、完成后的人工验证

脚本说「0 孤儿」不等于 Obsidian 里看着对。

**必做的人工验证**：
1. 在 Obsidian 里打开图谱，确认没有节点散在外圈
2. `Ctrl+O` 输入文件名，确认能跳转到正确的文件
3. 点开几个 cluster 段，确认 wikilink 真的能跳转（不是死链）

**脚本和 GUI 的渲染逻辑不完全一致**。以 GUI 为准。
