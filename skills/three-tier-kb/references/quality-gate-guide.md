# 质量门禁指南

12 项检查。目标不是「全绿」，而是**「退化看得见」**。

---

## 一、为什么是门禁而不是「整理一遍」

知识库不是一次性工程。它会持续退化：

- 新文件进来，没登记 → 变成孤儿
- 文件改名，旧链接没改 → 变成断链
- 有人重排目录 → 一批链接全断
- 复制了密钥文件进来 → 安全事故

这些退化**不会主动报错**。库看起来还是那个库，但检索体验在悄悄崩塌。

门禁的作用是把「我以为它还好」变成「我验证过它还好」。

---

## 二、12 项检查清单

| # | 检查项 | PASS 条件 | 失败含义 |
|---|---|---|---|
| 1 | 库结构与入口 | 有索引或总导航 | 没有入口 = 新 agent 接入会迷路 |
| 2 | 孤儿文件 | 孤儿数 = 0 | 有入链无出链的文件会被力导向布局推到边缘 |
| 3 | 断链 | 断链数 = 0 | 指向不存在文件的链接 |
| 4 | frontmatter 9 字段 | ≥90% 齐全 | 缺字段 → 无法被程序化检索 |
| 5 | 出链覆盖 | ≥80% 的卡有出链 | 库是一堆死文件 |
| 6 | 入链覆盖 | ≥70% 的卡被引用过 | 图谱是散的 |
| 7 | 敏感文件与凭据 | 无 | **安全红线，必须 FAIL** |
| 8 | 重复标题 | 无重复 | 同名文件会让「按标题找」变成随机行为 |
| 9 | 空文件 / 近空文件 | 无 | 噪声节点 |
| 10 | 日期有效性 | 无未来日期 | 未来日期通常是手滑或模板没改 |
| 11 | 索引一致性 | 元索引 MD 数 = 实际 MD 数 | 基线过期，新文件没进索引 |
| 12 | 图谱密度 | ≥2.0 出链/节点 | 结构稀散 |

## 三、第一次跑必然 FAIL —— 这是设计

```
检查结果：4 PASS / 7 WARN / 1 FAIL（共 12 项）
❌ 拦截：有 FAIL，禁止带病上线，回滚该批后重跑
```

**这不是 bug，是预期行为。** 一个真实存在的库，第一次体检必然发现问题。

正确的用法：

```
第 1 轮：跑门禁 → 拿到具体缺失文件清单
第 2 轮：修最容易的（孤儿归零）
第 3 轮：补 frontmatter
第 4 轮：修断链
...
第 N 轮：FAIL = 0 → 放行
```

**预期迭代 3-6 轮。** 追求一轮过是错的。

## 四、修复优先级

按「投入产出比」排，不按严重程度排：

| 优先级 | 项目 | 理由 |
|---|---|---|
| **P0** | 敏感文件（第 7 项） | 安全问题，必须立刻清 |
| **P0** | 孤儿文件（第 2 项） | 直接影响检索体验 |
| **P1** | 断链（第 3 项） | 图谱完整性的基础 |
| **P1** | frontmatter（第 4 项） | 程序化检索的前提 |
| **P2** | 出链/入链（第 5、6 项） | 图谱质量 |
| **P2** | 索引一致性（第 11 项） | 跑一次 `--build` 就好 |
| **P3** | 重复标题（第 8 项） | 存在但不致命 |
| **P3** | 空文件（第 9 项）、日期（第 10 项） | 清理类 |

**技巧**：第 11 项（索引一致性）跑一次 `kb_index.py --build` 就自动 PASS，
不需要手工修。**先跑 build 再跑 gate**，能省掉一大半 WARN。

## 五、9 字段 frontmatter 规范

```yaml
---
title: <文档标题>              # 必须
type: <项目索引|技术方案|复盘|...>  # 必须
owner: <负责人>                # 必须
status: <active|paused|completed|blocked|archived|in_progress>  # 必须
version: 1.0                  # 必须
effective_date: YYYY-MM-DD    # 必须
review_date: YYYY-MM-DD       # 必须，到期强制复核
source: <来源URL/路径/会话ID>   # 必须
confidentiality: <public|internal|confidential|secret>  # 必须
---
```

**为什么要 9 个字段这么严**：
- `source` —— 没有来源的文档无法验证真伪
- `effective_date` + `review_date` —— 知识会过期，没有复核日期的文档会永远假装新鲜
- `confidentiality` —— 让门禁能拦住不该进库的东西
- `owner` —— 知道找谁问
- `version` —— 知道这是第几版

**实战数据**：一个数百文件的库，frontmatter 完整率从 **8% → 52% → 100%**
用了三轮。批量补齐时用统一模板，不要手工逐个改。

## 六、第 7 项：敏感文件扫描

这是**唯一必须 FAIL 的项**，其他项都可以 WARN 过渡。

```python
SENSITIVE_NAME = re.compile(
    r'(\.env|credentials|secret[_-]?key|api[_-]?key|access[_-]?token|'
    r'\.pem$|\.key$|id_rsa)', re.I)

SENSITIVE_CONTENT = re.compile(
    r'(sk-[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}|ghp_[A-Za-z0-9]{30,}|'
    r'-----BEGIN [A-Z ]*PRIVATE KEY-----)')
```

**名称 + 内容双重检测**：
- 只查文件名 → 漏掉 `config.json` 里的密钥
- 只查内容 → 漏掉二进制密钥文件

**处置原则**：日志只写**路径**，不写内容。门禁报告里出现密钥本身也是泄露。

## 七、第 12 项：图谱密度阈值为什么是 2.0

```
密度 = 总出链数 / MD 文件数
```

实测：每个文件 **≥3 条出链**时，在 Obsidian 力导向布局中稳定居于中心区域。
**2.0** 是「结构健康」的保守下限。

| 密度 | 状态 | 典型原因 |
|---|---|---|
| ≥2.0 | 健康 | 有 cluster 互链 |
| 1.0-2.0 | 偏稀 | 卡片是列表不是网络 |
| <1.0 | 散架 | 每个文件孤立 |

**提升密度的唯一正确方式**：在项目索引里建 cluster 互链，
**不要**在正文里硬塞链接（那会污染内容）。

## 八、批量修复的安全姿势

```bash
# 1. 备份
cp -R ~/Documents/my-vault /tmp/kb_batch1_backup-$(date +%Y%m%d-%H%M%S)

# 2. 改（用 DOM 解析，不用正则）

# 3. 立刻验证
python3 $S/kb_gate.py ~/Documents/my-vault

# 4. 有 FAIL 就回滚
```

> **真实教训**：曾用正则批量扫描改写 Markdown 正文中的 HTML 结构，
> 一次操作损坏 28 篇文章。**Markdown 里嵌 HTML 时，禁止用正则扫描改写**，
> 必须用 DOM 解析（BeautifulSoup / lxml）。

**人工标注段的保护**：

```markdown
<!-- AUTO-INDEX-START -->
（脚本自动生成的内容）
<!-- AUTO-INDEX-END -->
```

脚本只在这个标记之间写入，手写内容永远不动。

## 九、门禁进 cron

```bash
# 每日基线重建后跑门禁
python3 $S/kb_index.py --vault ~/Documents/my-vault --build
python3 $S/kb_gate.py ~/Documents/my-vault
```

**FAIL 时才打扰用户**，PASS/WARN 保持静默：

```
✅ PASS  → 静默
⚠️ WARN  → 静默（记录到日志）
❌ FAIL  → 立即通知
```

这是「守护进程」的正确行为，不是「沉默」。

## 十、解读一份门禁报告

```
[2/12] 孤儿文件（无入链且无出链）...
  ⚠️  WARN  孤儿 2 个: 空文件.md、智能体/AgentB/项目/项目Beta/孤儿文件.md
```

逐项问三个问题：

1. **这些文件应该存在吗？** 不该存在 → 删（需用户授权）
2. **它们该挂到哪个索引？** 该存在 → 在对应项目索引里加 wikilink
3. **是批量问题还是个别问题？** 批量 → 写脚本批量修；个别 → 手工修

**注意**：孤儿文件检查会**自动排除**文件名含「索引」/`index`/`AGENTS` 的文件 ——
索引文件本身就是枢纽，它指向别人，没人指向它是正常的。
