# 三层架构深度解析

> 来自真实 vault 实践：数十个项目、数百个文件、数千条 wikilink、多套 AI 客户端、数十轮同步迭代。

---

## 一、问题的真正形态

「我想建个知识库」听起来是个写作问题，其实是三个独立的工程问题：

| 症状 | 真实问题 | 本质 |
|---|---|---|
| 「找东西要找很久」 | 全库扫描 O(n) | **延迟**问题 |
| 「搜出来 200 条，不知道看哪条」 | 没有优先级 | **排序**问题 |
| 「A 客户端和 B 客户端查出来不一样」 | 各查各的 | **一致性**问题 |

一个方案只能解决一个。三层架构同时解决三个。

---

## 二、每层的职责边界

### L0 · 元索引（机器层）

**它是什么**：3 个 JSON 文件，是全库结构的**物化视图**。

```
.kb_meta/
├── vault_index.json    项目 → 索引文件映射 + 全库统计
├── topic_index.json    主题关键词 → 文件集合
└── graph_index.json    节点数 / 边数 / 孤立节点清单
```

**为什么用 JSON 而不是 Markdown**：
JSON 可以被脚本以 O(1) 读取，不需要解析 frontmatter 和正文。
Markdown 索引更适合**人读**，JSON 索引更适合**机器读**。两者职责不同，都要。

**它为什么能被信任**：
因为它**可重建**。任何时候 `kb_index.py --build` 从 L2 全量重建，
30 秒内得到与磁盘完全一致的结果。所以索引漂移不是灾难，只是「再跑一次」。

**它什么时候会坏**：
- 两次基线之间新增了文件 → `vault_index.json` 的 `total_md_files` 落后
- 门禁第 11 项专门检测这个漂移

---

### L1 · 项目索引（语义层）

**它是什么**：每个项目目录下一个 `索引.md`，是这个项目的**人工导航**。

**为什么必须有这一层（这是最容易做错的地方）**：

L0 是关键词匹配的产物。关键词能告诉你「哪个文件里出现了 `some-site-name`」，
但**不能**告诉你「这个项目现在推进到哪一步了」「哪些产物是同一批次的」
「这个文件该归哪个项目」。

这些全是**语义判断**。AI 做全库扫描做不出可靠语义判断，人（或定向 AI 逐项目处理）可以。

> 真实教训：用 subagent 并行给每个项目生成索引，比一个 agent 顺序处理快 8 倍，
> 且遗漏率更低。批量同类工作时，并行 subagent 是默认选择。

**L1 的写法要求**：
1. 必须包含 **≥3 条出链**（见 `graph-view-repair.md`，这是力导向布局的阈值）
2. 必须列出**文件分组**（按批次/类型 cluster），不要只列文件清单
3. 必须在 frontmatter 里写 `title` / `type` / `status`，让门禁能识别

---

### L2 · 原始内容（真相层）

vault 里的全部 Markdown。它是**唯一不能丢的东西**。

L0、L1 都是它的派生视图。删掉 L0，重新 `--build` 就回来了；
删掉 L1，人重写一遍就行；删掉 L2，**不可恢复**。

## 三、查询路由：为什么 L0 永远优先

考虑查询「视频」：

- L0 命中：`topic_index.json` 里 `视频` 主题 → 直接给出该项目 + 相关文件集合
- L1 命中：每个项目的 `索引.md` 里提到「视频」
- L2 命中：300 个 MD 里都出现「视频」

如果按 L2 优先，用户拿到 300 条噪音。
如果按 L0 优先，用户拿到「短视频项目 + 12 个相关文件」。

**规则：同一关键词命中多层时，L0 优先，L1 次之，L2 兜底。**

实现上就是简单的三层结果拼接 + 去重：

```python
merged = level_0 + level_1 + level_2   # 顺序即优先级
seen = set()
final = [x for x in merged if not (x['path'] in seen or seen.add(x['path']))]
```

## 四、会话库 FTS5（跨层检索）

「我之前说过 X 吗」这类问题不在 vault 里，在**会话历史**里。

```python
# ❌ 错误写法 —— 没有 JOIN FTS5 虚拟表
SELECT s.id, m.content FROM messages m WHERE messages_fts MATCH ?

# ✅ 正确写法 —— 通过 rowid JOIN
SELECT s.id, m.content, s.started_at, m.role
FROM messages_fts mf
JOIN messages m   ON m.id = mf.rowid
JOIN sessions s   ON m.session_id = s.id
WHERE messages_fts MATCH ?
  AND m.role = 'user'
  AND s.started_at > ?
ORDER BY s.started_at DESC
LIMIT 10
```

**四个必须记住的细节**：
1. FTS5 的 `MATCH` 走全文索引，**不会**做 LIKE 语义
2. **中文必须用 `tokenize='trigram'`**，默认 `unicode61` 会把中文切成单字，精度极差
3. 一定要 `LIMIT`（10-20）且加 `m.role='user'`，否则助手的长回复会淹没用户原话
4. `started_at` 是 unix epoch，用 `time.time() - N*86400` 做时间截断

## 五、数据流全景

```
        ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
        │ Hermes       │  │ Codex CLI    │  │ Trae IDE     │   ← 多个 AI 客户端
        └──────┬───────┘  └──────┬───────┘  └──────┬───────┘
               │                 │                 │
               └────────┬────────┴────────┬────────┘
                        │  kb_sync.py      │  每 5 分钟
                        │  (哈希基线增量)    │
                        ▼                 ▼
              ┌─────────────────────────────────────┐
              │           L2 · 原始内容 (vault)        │  ← 唯一真相源
              │   智能体/<客户端>/项目/<项目>/          │
              └───────────────┬─────────────────────┘
                              │ kb_index.py --build（每日基线）
                              ▼
              ┌─────────────────────────────────────┐
              │           L0 · 元索引 (JSON)           │  ← 可重建缓存
              │  vault_index / topic_index / graph_index │
              └───────────────┬─────────────────────┘
                              │ 查询路由（L0 优先）
                              ▼
              ┌─────────────────────────────────────┐
              │           L1 · 项目索引 (索引.md)       │  ← 语义层，人写
              └─────────────────────────────────────┘
```

## 六、架构决策记录（为什么没选另一条路）

| 决策 | 备选 | 选择 | 理由 |
|---|---|---|---|
| 从零重建基线 | 增量更新索引 | **从零重建** | 增量漏一次删除就永久漂移；从零重建永远自愈 |
| 5 分钟 cron 同步 | 实时文件监听 | **cron** | 监听在并发写入时锁竞争严重、难调试；cron 窗口够小且可回溯 |
| 项目索引由人/定向 AI 写 | 全库 AI 自动分类 | **定向 AI** | 全库自动分类语义不可靠，误分类的修复成本远高于人工确认 |
| 同目录 cluster 互链 | 跨目录同类互链 | **同目录** | 同目录文件天然相关，形成密集网络而非散点 |
| L0 用 JSON | L0 用 Markdown | **JSON** | 机器读要 O(1) 解析；人读用 L1 Markdown |
| 不建独立资源索引 | 每类资源建索引文件 | **内嵌 wikilink** | 独立索引文件必然成为孤儿节点 |
